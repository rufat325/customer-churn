# Deployment

How this is deployed publicly, and why that is a defensible choice here.

---

## 1. Is it safe to leave open?

**In this project, yes — because the data is invented.** Every customer is
generated by `src/generate_data.py`. There is no real person in the dataset, so
a public dashboard exposes nothing about anybody.

That reasoning does not transfer. With real customers, `GET /customers` paging
through ids, spend, order history and churn scores without authentication is a
data breach, not a demo. If you fork this for real data, turn on the password
(§6) and keep it on.

What being public still costs, even with fake data:

| Risk | Mitigation here |
| --- | --- |
| Anyone can make your server do work | Per-IP rate limit, 120 req/min by default |
| Model extraction — enough queries reconstruct the model | Same rate limit; the model is a toy anyway |
| Someone changes something | Nothing to change: every endpoint is read-only |
| Credentials sniffed in transit | HTTPS via Caddy (§4) |

## 2. Ports, and the one that surprised us

The container **always** listens on 8000 internally. Only the host mapping
changes, which is why the local dev server ended up on 8010 — Docker Desktop
already held 8000 on that machine:

```bash
docker run -d -p 8010:8000 customer-churn:latest    # laptop, 8000 busy
```

Nothing in the image needs changing between environments.

For the real deployment you do not publish 8000 at all. Caddy listens on 80 and
443, and reaches the API over the private compose network. That is not cosmetic:
if 8000 were reachable directly, a caller could skip TLS *and* forge the
`X-Forwarded-For` header the rate limiter reads to identify them.

### Security group

| Port | Source | Why |
| --- | --- | --- |
| 22 | **your IP only** | SSH. Never `0.0.0.0/0`. |
| 80 | `0.0.0.0/0` | HTTP, needed for the Let's Encrypt challenge and the HTTPS redirect |
| 443 | `0.0.0.0/0` | the actual site |
| 8000 | **remove this rule** | was the old direct-exposure setup; delete it |

That last row matters. The earlier deployment opened 8000 to the world, which
is what made the unauthenticated API reachable from any device.

## 3. Build the image

The image copies `models/` at build time, so a trained artifact must exist
before you build.

**Recommended — build on your machine, ship the image.** A `t3.micro` has 1 GB
of RAM and one vCPU; a scikit-learn grid search on it is slow at best and gets
OOM-killed at worst.

```bash
python src/generate_data.py && python src/train.py
docker build -t customer-churn:latest .
docker save customer-churn:latest | gzip | ssh -i key.pem ec2-user@YOUR_IP 'gunzip | docker load'
```

**Alternative — build on the instance.** Needs Python plus the dev
dependencies, and an instance with real memory (`t3.small` or larger):

```bash
pip install -r requirements-dev.txt && python src/generate_data.py && python src/train.py
docker compose -f deploy/docker-compose.yml build
```

## 4. Run it with HTTPS

Browsers flag plain HTTP, and HTTP Basic over it sends the password in the
clear. You want a certificate.

**No domain?** You do not need one. Wildcard DNS services resolve an
IP-derived hostname to that IP, so `1-2-3-4.nip.io` points at `1.2.3.4` with no
registration and no DNS configuration — and Let's Encrypt will issue a
certificate for it, because it resolves publicly.

Substitute your instance's public IP, dots replaced by dashes:

```bash
SITE_ADDRESS=1-2-3-4.nip.io docker compose -f deploy/docker-compose.yml up -d
```

Caddy obtains and renews the certificate itself. The site is then at
`https://1-2-3-4.nip.io`, openable from any device, with a padlock.

Omit `SITE_ADDRESS` and it serves plain HTTP on port 80 instead — fine for a
local test, not for anything you hand out.

> **An Elastic IP is worth attaching.** Without one the public IP changes every
> time the instance stops, and the hostname baked into your certificate stops
> matching.

## 5. Verify from outside

Do this on a phone with **wifi off**, so you are testing from an address that
is not your whitelisted one:

```text
https://1-2-3-4.nip.io/health
```

Expect `{"status":"healthy", ...}` including a `protection` block showing which
guards are active. Then open the root for the dashboard.

To confirm 8000 really is closed:

```bash
curl --max-time 5 http://YOUR_IP:8000/health
```

A timeout is the correct result.

## 6. Turning protection on

Both switches are environment variables, both off by default, because a
portfolio demo exists to be opened by strangers.

**Password on everything** — browser prompts, `curl -u` works, `/health` stays
open so the container health check keeps passing:

```bash
SITE_ADDRESS=1-2-3-4.nip.io CHURN_PASSWORD=pick-something-long \
  docker compose -f deploy/docker-compose.yml up -d
```

**API key on the scoring endpoints only**, leaving the dashboard browsable:

```bash
SITE_ADDRESS=1-2-3-4.nip.io CHURN_API_KEY=$(openssl rand -hex 24) \
  docker compose -f deploy/docker-compose.yml up -d
```

**Tighter rate limit**, if you are being hammered:

```bash
CHURN_RATE_LIMIT=30 docker compose -f deploy/docker-compose.yml up -d
```

Only set `CHURN_PASSWORD` alongside a real certificate. Basic auth over plain
HTTP is base64, not encryption — anyone on the path reads it.

---

## 7. Locking it down or shutting it off

**Restrict to yourself:** change the port 443 source from `0.0.0.0/0` to
`My IP` in the security group. Instant, reversible, no redeploy.

**Stop the instance:** EC2 console → Instances → Instance state → Stop. Storage
still bills at a few cents a month; compute stops. Release the Elastic IP too —
AWS charges for ones not attached to a *running* instance.

**Cost note.** Past the 12-month free tier, a `t3.micro` running continuously
is roughly \$8–10/month. If this is only occasionally demoed, stopping it
between demos is the cheaper habit, and screenshots in the README show the same
thing for free.

## 8. Checking on it

```bash
docker compose -f deploy/docker-compose.yml ps
docker compose -f deploy/docker-compose.yml logs -f api
docker compose -f deploy/docker-compose.yml logs -f caddy
```

Every API line carries a request id, path, status and duration; rejected
requests are logged at warning level with the client IP, so a burst of 429s is
visible. Caddy logs certificate issuance and renewal.
